Part A · The flow

01

The flow at a glance

Six phases, top to bottom. Claude runs each phase; nothing moves to the next one without the decision shown on the right. The one loop that is not drawn: any code change after verify sends the touched scope back to phase 3, then on to phase 4 as usual.

02

Phase by phase: what you give, what Claude does, what you get

Each phase ends with something concrete you can act on. The "you get" column is the hand-over.

1. Brief and plan

Starts when: you describe the task

You give

  • A ClickUp card link, a Figma frame, a defect list, or a plain description.
  • The card's checklist is the acceptance criteria; its r{xx} mid|end tag decides the PR title later.

Claude does

  • Fetches the card with checklists and attachments.
  • Surveys origin/develop, the hotfix gap to main, and open PRs, never the main checkout.
  • Big work: a map or an OpenSpec proposal that ends in a tasks.md.
  • Answers any question in plain text before asking its own.

You get

  • A written scope and task list.
  • Crux decisions one at a time; low-stakes gaps as one numbered list with a recommendation each. You reply with the numbers you reject.

2. Apply

Starts when: a go-word is in your current message (apply, แก้เลย, ทำเลย …)

You give

  • The go-word. Questions, tone, momentum, and earlier go-words never count.
  • Optionally arm session to keep the gate open until you say lock.

Claude does

  • Works in a private worktree .worktrees/wt-<port>; the main checkout belongs to GitKraken.
  • Says the routing line; delegates implementation when a tasks.md exists, edits itself only for 2 files / 30 lines or less.
  • Walks tasks.md against the real diff hunks when an implementer returns. A ticked task is a claim, not evidence.
  • Runs lint and tsc.

You get

  • The diff, the weight line, memory proposals, "HANDOFF.md updated".
  • Heavy: the review report first, before verify.
  • Blocked by the gate: the ready diff and "type apply".

3. Verify

Starts when: you say verify, and choose here or a new session (the choice holds for the rest of the task)

You give

  • The verify go and the session choice.
  • A yes when Claude asks before touching your infra (DB tunnel, dev servers, ngrok).

Claude does

  • Prepares and proves the environment, writes a brief, dispatches a verifier, judges the result against the code.
  • Full table in the next section.

You get

  • Screenshots as files plus a checklist table: covered / partial / not covered, with evidence per item.
  • You tick ClickUp yourself; Claude never ticks unverified items.

4. Deliver

Starts when: you invoke /deliver-finished-task, or give one go-word after the verify-end diff

You give

  • One go for the whole chain. Claude never re-asks per step and never opens a PR on intent stated earlier.
  • Answers to one batched question when values are unknown (base branch, PR title sprint tag).

Claude does

  • Runs the code review (skipped when it already ran on the same code), commits with conventional messages, pushes, opens the PR, assigns you.
  • States source → target before any push.
  • Stops only when blocked: red lint/tsc, no verify yet, conflict, or a force-push would be needed (you run that command yourself).
  • Removes the worktree in the same turn the push lands.

You get

  • A PR titled by rule: [SP{xx}:RM|RE] branch, [Bugfix] - slug, or twin [Hotfix] - slug PRs to main and qa2.
  • A body with Scope, Decisions, Verification record, screenshots by hosted URL, and any merge dependency. No AI attribution.

5. After the PR

Starts when: review bots or teammates comment

You give

  • "Reply to the comments" or a decision on a bot's proposed fix.
  • The merge, and the qa sync in GitKraken.

Claude does

  • Verifies each finding against the code before answering; replies in Thai with a model footer; resolves only the threads it replied to.
  • A follow-up fix re-runs verify only for the scope the new diff touches.
  • Hotfix follow-ups stay on the same hotfix branch; qa2 never flows back to main.

You get

  • Threads answered with evidence, and a re-verified diff where one was needed.
  • A PR that stays mergeable; direct pushes to develop/main/qa only on explicit permission per instance.

6. Close

Starts when: you say stop, or ask for a handoff

You give

  • "stop" ends the session; "handoff" asks for the resume package.
  • Confirmation on memory proposals.

Claude does

  • Three lines: git and PR state, what is pending, merged or not.
  • Removes the handoff directory and scratch files once nothing is pending.
  • Offers a retro when the session showed a signal.

You get

  • On "handoff": HANDOFF.md plus a paste-ready resume prompt with SHAs, next steps, environment bring-up, pending memories.
  • A memory set trimmed to what still helps the next task.
03

Verify in detail

Seven steps. Steps 1 to 3 and 5 to 7 run in the main session; step 4 is a subagent. Each step produces something the next one, or a later phase, consumes.

StepProducesConsumed by
1 Preflight envA server on the worktree's port, with a real install, Prisma client generated, .env loaded through envrun, CORS allowlisted, test data present.The verifier. It never repairs the environment; it stops and reports, the main session fixes, and continues the same agent.
2 Smoke checkProof that the served code is the code under test: the server's cwd is the worktree (lsof -a -p <pid> -d cwd), a feature symbol greps in that tree's .next, and no other port is baked into its chunks.Pasted into the brief. 4 Subagent runsPNGs per scenario, a report, reusable Playwright scripts, and a list of database SELECTs it could not run, all under ~/.claude/handoffs/<task>/verify/.Step 5. The SELECTs are run by the main session after hand-back.
5 Hand-back checkAn outcome (correct / partial / blocked / wrong) from reading the full final message against the code, and one row in the dispatch ledger.The decision whether this verify counts. The Sunday retro.
6 Report to youScreenshots sent as files, the checklist table with evidence per item, HANDOFF.md updated.You tick ClickUp. The table becomes the PR body's Verification record. Verify-end is where you give the deliver go.

The loop. Any change after step 6 voids the verify for the scope the diff touches: changed files plus their callers, derived from the diff, never from the fix's intent. Back to step 3 with the same brief and a smaller scope. A pure-function fix gets smaller still: show the normal path still returns what it did, then one runnable check that fails on the old code.

Part B · The machinery

05

How work is split: main session and subagents

The main session is the orchestrator. Execution goes out by lane, on a model chosen by the shape of the work, with a brief that carries everything the agent needs and a budget it counts itself.

Who does what

The main session (the frontier model) owns scope, planning, every brief, the review of what a subagent returns, every decision, all git and PR actions, and the environment a subagent will use. It edits code itself only for 2 files / 30 lines or less, and only when no tasks.md exists. Everything else is dispatched by lane: research, verify, apply (implement), review.

Two questions decide the model, said out loud in the routing line

  1. Does the work have an adaptive loop: a running environment, tests to make green, a spec to interpret, "if X fails do Y" in the brief?
  2. Would a wrong result be cheap to catch with one grep or one command?

Opus when the answer to 1 is yes or to 2 is no: verify, implement with a test loop or a multi-layer diff, why/architecture research, risky whole-branch review, escalation after one blocked result. Sonnet when the brief is mechanical and the result is re-checked in one command: locate-only research, tasks that already name the file and the value, TDD loops with the tests written first, reruns of a script that already passed. Haiku for pure runners. Fable only after Opus is blocked. "Needs judgment" is never a reason to keep work in the main session: it means the spec has a gap, so the spec gets fixed and the work still goes out.

What every brief carries

Proven facts (URLs, ports, ids, paths, how to load .env), a non-overlapping scope, a stop budget as a tool-call cap the agent counts itself (default 120, never minutes alone, because an agent cannot see its own turn count), the evidence path, and a 10-line return format. Subagents share the session's edit-gate arm, so implementers that touch repo files run in the foreground. A subagent never repairs the environment; it stops and reports, and the main session fixes and continues the same agent.

After hand-back

A ticked task is a claim: the main session walks tasks.md against the real diff hunks before any review or verify. Follow-ups that need context not yet on disk go back to the same agent; reruns of an existing script go to a new agent with the same brief, because a resumed agent drags every earlier round into each turn. One ledger row per hand-back, outcome judged against the code.

Research on 2026-10-08 found no vendor recommending it for subagents; every built-in splits by lane, and repo conventions already load from the working directory, so role bodies would only duplicate them. 07

Always on: not in the flow, checked every turn

These never appear as a phase. They run on every message or at every unit boundary (apply-end, verify-end, PR delivered, close), whatever phase the task is in. Each one is a side channel that reports and waits for you; none of them changes anything on its own.

every turn · silent under 180k

Context meter

Usage is measured at the start of every turn. Under 180k nothing is said. From 180k, one line appears only at a unit boundary or the first turn past each new 50k step: the measured number, whether the next unit is related, and a recommendation to stay or move to a new session. You decide; Claude follows without re-arguing.

unit boundaries · needs your confirm

Memory candidates

At apply-end, verify-end and close, Claude proposes what is worth remembering for future workflow, starting with "checked existing memory: none / see X". "Nothing worth saving" is a valid proposal. Nothing is written until you confirm. After a PR merges, Claude proposes trimming that task's memory to surviving gotchas.

every execution moment

Routing line

The first line of any reply that starts work says who does it: → delegate: Opus (verify — adaptive loop) or → self: <reason>. The rule behind it is in section 05. The model is always pinned.

every subagent hand-back

Dispatch ledger

One row per hand-back: model, lane, weight, turns, cost, wall time, and an outcome (correct / partial / blocked / wrong) judged against the code, never taken from the agent's own claim. The Sunday retro reads this file; a dispatch missing from it is invisible.

every unit boundary · silent

HANDOFF.md

Rewritten at every unit boundary with one line in chat. It is the insurance against a dead session. The ready-to-paste resume prompt is written only when you ask for a handoff, never offered unprompted.

every message · hooks

Prompt hooks

Three scripts run on every message you send: the go-word check that arms the edit gate for one round, a git-state line injected after a gap of 10 minutes or more, and a terse-reply rule matched to the language of your message. None of them blocks; they shape the turn before Claude reads it.

apply-end · one line

Weight line

weight: light|heavy — <files, shared consumers, contract, regression scope>. Light goes straight to verify. Heavy runs the code review before verify, because a finding fixed after verify voids the verify. You can override the weight in one word.

session close · on a signal

Retro offer

When a session shows a signal (the same correction twice, a fact that took several tool calls to find, an environment fixed by hand, cost above the usual band), Claude offers a quick retro. How that works is section 08.

08

The weekly retro: how the workflow changes itself

Three loops, each one read-only. Nothing changes without a go-word in a live session, and every change lands with the date and the incident behind it.

  1. Quick retro, per session, on a signal. The same correction twice, a fact that took several tool calls to find, an environment fixed by hand, cost above the band. retro-run dispatches a read-only Opus reader (Read, Grep, Glob only) over one transcript with a 7-axis rubric: navigation, automated checks, standards, steering size, tool economy, information access, delegation. Each candidate is classed mechanical (a hook or lint can catch it), judgement (needs a rule), or no-op (a rule nobody needed, candidate to delete). Report to workflow-reviews/quick/, one ledger row, nothing applied.
  2. Sunday retro, 21:30, scheduled. A script digests every transcript of the week; one Sonnet analyst per batch; ledger numbers per lane and model (which model was cheaper per correct result, and whether that agrees with the routing rule); parked items from agenda.md; the week's quick retros as evidence. One report, workflow-reviews/YYYY-MM-DD.md, with a fixed numbers table against the previous week and the sprint so far: sessions, human turns, real gate blocks and same-turn retries, sessions with an Agent call, Agent calls without a model, share of messages in long sessions. A finding needs two or more occurrences unless the user parked it on purpose. Report only.
  3. Decision, in a live session. The user picks items with a go-word. Destination by class: mechanical goes to a hook or lint; judgement goes to CLAUDE.md or the repo's reviewer rules; our-workflow questions go to agenda.md for the next Sunday. Every decision lands in working-agreement-history.md with the date and the incident, so the rule file stays rules-only and the reasons survive.

What came out of it recently

  • One delivery gate instead of three (2026-09-26).
  • Side effects outside the repo need the same go as edits (2026-10-05).
  • Wayfinder batches low-stakes gaps into one list with a recommendation each (2026-10-05).
  • retro-run itself, after a third-party retro skill turned out to scan transcripts in the main session (2026-10-07).
  • The context line now reports a measured number at boundaries instead of a guess (2026-10-07).

Part C · Running it yourself

09

Dependencies: what you need to run this

Split by what breaks without it. The required set is small; most of the behaviour comes from the rule file and seven Python scripts.

Required

  • Claude Code, desktop app or CLI, with the rule file at ~/.claude/CLAUDE.md.
  • python3 for the hook scripts in ~/.claude/scripts/, wired in ~/.claude/settings.json.
  • git and the gh CLI: PR create, edit, assign, thread replies.
  • pnpm for every repo; lsof for the smoke check and the dev-server gate.
  • Playwright with channel: 'chrome' for verify screenshots.
  • launch.json entries per worktree port (tqm-main-web-wt-3001, -wt-3002).
  • envrun (ships with the scripts) to use .env values without reading them.

Optional plugins (installed here)

  • superpowers: brainstorming, TDD, systematic debugging, plan execution.
  • ponytail: the "laziest solution that works" stance on every code task.
  • context-mode: large tool outputs kept out of context. Caveat: it truncates big Bash output and blocks curl inconsistently.
  • claude-mem: cross-session search of past work.
  • serena: symbol-level code navigation.
  • pordee / caveman: terse replies in Thai or English.
  • lowfat (Homebrew): trims git/ls/find output before it reaches Claude.

Skills and connectors

  • Own skills in ~/.claude/skills/: deliver-finished-task, verify, review-before-deliver, retro-run, handoff, fix-ui-defects, share-local-demo, PR listing and triage.
  • The skills-CLI set linked from ~/.agents/skills: wayfinder, grilling, pr-review, tdd, research.
  • OpenSpec (opsx:*) in each repo for propose / apply / archive.
  • MCP connectors: ClickUp (cards, checklists), Figma (frames, assets), Slack (threads). GitHub goes through gh.
  • The repo-side .claude/ in tqm-main-web: launch entries, repo skills, the code-reviewer rules.
  • The Sunday retro: a scheduled task plus session-digest.py and the batch prompt in ~/.claude/scripts/; the retro-reader agent definition in ~/.claude/agents/.

Glossary

go-word
A word in your current message that permits file edits for one round: apply, go ahead, fix it, ทำเลย, แก้เลย and the others in edit-gate-words.txt. Earlier messages never count.
unit boundary
A point where one unit of work ends and you decide the next: apply-end, verify-end, propose-end, PR delivered, session close. Sidecars report only here.
weight
light or heavy, said in one line at apply-end. Heavy means whole-flow change, wide impact, or a shared component with many consumers. Heavy gets the code review before verify.
worktree port
A private git worktree at .worktrees/wt-<port> served by a permanent launch entry on that port. The main checkout is never served or committed from by a session.
lane
The kind of work a dispatch does: research, verify, apply, review. The ledger and the routing rule are organised by lane, not by job role.
brief
The instructions handed to a subagent: proven facts, scope, evidence path, a tool-call budget it counts itself, and the model. Written by the main session; reusable for reruns.
hand-back
The moment a subagent returns. Its claims are checked against the code before anything is believed, and one ledger row is written.
smoke check
Proof, before dispatch, that the running server serves the worktree under test: process cwd, a feature symbol in its build output, no foreign port in its chunks.
routing line
The first line of a reply that starts execution: who does the work and why, with the model named.
sidecar
Anything that runs every turn or at every boundary without being a phase: context meter, memory proposals, ledger, HANDOFF.md, prompt hooks.
ledger
~/.claude/dispatch-ledger.tsv: one row per subagent hand-back. The Sunday retro's only source for delegation numbers.
