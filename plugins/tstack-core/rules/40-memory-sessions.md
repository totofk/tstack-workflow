# Memory, handoff, sessions

What gets remembered, where, and how a session ends or resumes.

- Memory proposals are about future workflow utility, not fact preservation. Proposals are summarised first and wait for confirmation; "nothing worth saving" is valid. Every proposal starts with "checked existing memory: none / see X". A memory review is offered at a natural session end without being asked.
- Feature-level facts are not memory unless (a) they are not derivable from the repository, its docs or its graph (gotchas learned by doing, blast radius, machine-specific ids) and (b) they are stable beyond the current sprint — or the user orders it. The concern is index bloat: too many entries and none can be weighed. When a task's PRs merge, the assistant proposes trimming that task's memory to the surviving gotchas or deleting it, re-checking each claim against the base branches first.
- Routing by scope: workflow-level facts → the user-level rules or user memory; project gotchas → the repository's own knowledge file when it has one (a team adapter names it), else project memory; machine- or person-specific facts (ports, tunnels, test-row ids, which branch a checkout sits on) → project memory, never a team-shared file. Behavioural corrections default to user level. Misplaced entries are not migrated.
- The handoff file is kept current at every unit boundary (`<handoffs dir>/<task>/HANDOFF.md`, English): it is the insurance against a dead session. When the user asks for a handoff it is two pieces: the file and a ready-to-paste resume prompt in the chat reply — branch and PR state with SHAs, next steps with fill-in slots, environment bring-up (launch entries, worktree paths, tunnels and ports, test rows), pending memories, a one-line rules recap.
- A `start_session` brief says: reply to the user in Thai; and the call passes `model` explicitly (the field accepts only the parent's model or a cheaper one). A brief arrives in the new session as a pasted block, so its English does not set the chat language there.
- On resume after a gap the assistant prints the current git state (branch, ahead/behind, uncommitted) and the environment card unprompted, then asks what is ambiguous.
- When the user references past work not in context (a feature or ticket name, "the thing we did", "yesterday"), one search of the session memory runs before any question; at most two hits are opened, then only what is still missing is asked. No agent is dispatched to hunt transcripts for this.
- Context is measured every turn silently; the usage tool is called at the start of every turn, never an unmeasured estimate. Under 180k nothing is said. From 180k, one line — only (a) at a unit boundary (apply-end, verify-end, propose-end, PR delivered) or (b) the first turn after crossing a new 50k step (180k, 230k, 280k …), never mid-unit or on a one-line answer: `context Nk/1M (measured) · next: <related via <named shared thing> | unrelated> · <stay | new session, because <reason>>`. It is a warning plus a recommendation, never a decision: the user chooses to move (handoff plus resume prompt) or stay, and the assistant follows without re-arguing until the next line is due. Related = continuous work on one feature or PR at any size; moving is recommended when the next unit is long (many turns: apply, verify matrix, multi-repository delivery) or unrelated. A size question from the user gets the measured number and the same line.
- Automation requests are sized first: establish the frequency and what already catches the problem, then propose the smallest thing — often a rule, sometimes nothing. "Does this need to exist at all" is re-asked every iteration.
- Post-mortem is one exchange; forensics go to a cheaper agent. After a mistake: fix it, one line on the cause, move on. A "why" from the user gets one answer with evidence, not a series. Transcript, reflog and config scanning is mechanical and dispatched, never run in the main session. A quick retro (`retro-run`) is offered at the close of a session with a signal: the same correction twice, a fact that took several tool calls to find, an environment fixed by hand, cost above the usual band. Findings route by class: mechanical → a hook or lint; judgement → the rules file or the repository's reviewer rules; workflow questions → the retro agenda.
- Planning questions are batched when low-stakes: crux decisions go one at a time; gaps that each have a clear recommended answer go as one numbered list in plain language, each item with its recommendation, and the user replies only with the numbers they reject.
