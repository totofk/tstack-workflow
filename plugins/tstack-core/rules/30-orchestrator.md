# Orchestrator and subagents

How work is split between the main session and dispatched agents, and how every dispatch is recorded.

- The main session owns scope, planning, briefs, review of subagent output, decisions, and all git and PR actions (worktree, merge, conflicts — done before dispatch, on the worktree the implementer will use). It edits code itself only for changes of at most 2 files and 30 lines, and only when no `tasks.md` exists.
- "Needs judgment" is never a reason to keep work in the main session. Judgment the spec cannot answer is a spec gap: the spec is fixed, then the work is dispatched. Git needing judgment is the main session's job anyway and says nothing about who edits the code.
- The routing is said out loud: the first line of the reply at the execution moment is `→ delegate: <model> (<lane> — <reason>)` or `→ self: <reason>`, before any tool call. The agent description carries the same tag (`verify/opus`, `research/sonnet`). The user's "do it yourself" or "send a subagent" overrides.
- Dispatch ledger, one row per hand-back, no exceptions: `$CLAUDE_PLUGIN_DATA/dispatch-ledger.tsv` (a retro tool that still reads an older location gets a symlink from there) with columns date, session, agent, model, lane, weight, turns, cost, wall_min, outcome ∈ correct | partial | blocked | wrong, note. The outcome is the main session's judgment after checking the result against the code, never the agent's own claim. The weekly retro reads this file; a dispatch missing from it is invisible. The model column records the exact model id, never an alias: for a lane dispatch (`subagent_type` = verify / implement / research / tracking) with no `model` override it is the id the lane file resolves to (`claude-opus-5-5` / `claude-sonnet-5-5`); with an override, or for any other agent type, it is read from the subagent transcript.
- Every dispatch is weighed on two questions, answered in the routing line: (1) does the work have an adaptive loop (a running environment, tests to make green, a spec to interpret, "if X fails do Y" in the brief); (2) would a wrong result be cheap to catch with one grep or one command. The stronger model (Opus class) when 1 is yes or 2 is no: verify, implement with a test loop or a multi-layer diff, why/architecture research, risky whole-branch review, escalation after one blocked result. The cheaper model (Sonnet class) when the brief is mechanical and the result is re-checked in one command: locate-only research, tasks that already name the file and the value, TDD loops with the tests written first, reruns of a script that already passed. A lane is always passed as `subagent_type` (`verify` / `implement` / `research` / `tracking`, definitions in `~/.claude/agents/`); `model` only to override the file, and the override goes in the ledger note. The smallest model only for pure runners; the frontier model only after the stronger model is blocked. Never three stronger-model agents in parallel for routine verify.
- The cost driver is context × turns. Every brief carries proven facts (URLs, ports, ids, paths, how to load the environment), non-overlapping scopes, the stop budget is the lane file's `maxTurns` (verify / implement 120, research 80); a brief states a lower cap only for a small task; an overrun returns a partial result and goes in the ledger note. Report, evidence and reusable scripts land in the task's evidence directory; the return is at most 10 lines. Implementer briefs say: edit with Edit/Write only, never Bash heredocs or a python replace (the auto-mode instruction inside subagents says otherwise).
- Implement briefs are split by size: a batch above about 4 tasks or 3 files becomes one dispatch per group, each with its own budget and diff walk.
- Delegated edits: subagents share the session's gate arm. Implementers that edit repository files run in the foreground; verify and research may run in the background. Blocked mid-run → a new go-word, then the same agent continues. The gate is never routed around via shell.
- A ticked task is a claim, not evidence. When an implementer returns, the main session walks `tasks.md` item by item against the actual diff hunks (one hunk or file per task, named) before review or verify.
- Follow-ups after an agent returns go to the same agent only when the next step needs context that is not on disk yet (continuing a diagnosis, the next scenario of an unfinished script). A rerun of a script that already exists goes to a new agent with the brief and the script path: a resumed agent drags every earlier round's context into each turn. The main session runs a step itself only when the agent was blocked on that exact step, then hands the next step back.
- A rule change is measured: the plugin's usage scripts summarise turns, minutes, cost and outcome per dispatch; the outcome column is read from the agent's full final message, never keyword-matched.
