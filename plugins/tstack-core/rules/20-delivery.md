# Verify, commit, PR

The order of one unit of work and the gates between its steps. Team-specific values (PR title scheme, base branches, assignee, where acceptance criteria come from) are read through `workflow-config` (the repository's `.agents/workflow.json`, else a personal untracked `.claude/workflow.json`, else a team adapter's `workflows/<repo>.json`); the defaults below apply otherwise.

- Apply-end is a unit boundary, not a session end. After edits the assistant stops at lint and type-check, reports the diff and any memory proposals, and updates the task's `HANDOFF.md` with one line in chat ("HANDOFF.md updated"). The user decides where the next unit runs: "verify" or "verify here" means this session, and that choice holds for the rest of the task. The resume prompt is written only when the user asks for a handoff, never unprompted. A user's "stop" ends the session with three lines of git and PR state and what is pending. After a context summarisation the assistant says so in one line.
- Verify before commit or push. Order: apply → lint and type-check → weigh (one line) → [code review only when heavy] → ask → verify (with screenshots) → commit, push, PR. The review, when it runs, sits before verify on purpose: a finding fixed after verify voids it. When local verification is impossible the assistant says so and waits. Any post-verify change, however small, voids the verify for its impact area: only the scenarios whose code path the new diff touches are re-run (changed files plus their callers, derived from the diff, never from the fix's intent), and that scope is written into the brief. A pure-function fix is scoped smaller still: show the normal path returns what the old code returned, then prove the defect case with the smallest runnable check that fails on the old code. Behaviour outside the agreed scope surfaced mid-verify pauses the verify and asks.
- Weight, said out loud at apply-end: `weight: light|heavy — <files, shared consumers, contract, regression scope>`. Light = one file or few hunks, no shared consumers, no front-end/back-end contract → no review, straight to verify (user's call) → commit and PR. Heavy = whole-flow change, wide impact area, regression of half the feature or more, shared component with many consumers → the code review runs at apply-end before verify. The user can override the weight in one word.
- Screenshots with every verify, delivered as files the user can open (screenshots that live only in the assistant's tool results are invisible to the user). Under delegation the verifier captures PNGs to its evidence path and the main session sends them.
- Environment handoff contract. Before dispatching any subagent that needs a running system the main session makes it ready: server on the right port, environment file in the worktree, code generation done, test data present. Then one manual smoke check is pasted into the brief; a failed smoke means no dispatch. The smoke proves the served code is the code under test (server process working directory equals the worktree; a feature symbol greps in that tree's build output), not just an HTTP 200. The subagent never repairs the environment: it stops and reports, the main session fixes and continues the same agent.
- Verify serves a private worktree, never the main checkout (other sessions and agents share it): `git worktree add --detach .worktrees/wt-<port> <sha>`, served by a permanent launch entry per port; torn down in the turn the result is reported. Build output in a worktree is checked for another port baked in before dispatch (a build produced by another session's server keeps passing while that server is up and fails only when it stops).
- User-side infrastructure (database tunnels, shared dev servers, public tunnels) is asked about before the first command that needs it.
- Acceptance criteria come from the source named in `workflow.json` (`acceptance`: a ticket system, an issue, or the brief itself). Every item is reported as covered, partial or not covered with evidence; the assistant never ticks an item it did not verify. The user ticks.
- Delivery is one gate: the `deliver-finished-task` skill, user-invoked only. It runs the code review itself (skipped when it already ran on the same code), then commit → push → PR, or push and merge forward when the branch already has a PR. The invocation, or one go-word after the verify-end diff, is the go for the whole chain: no re-asking per step, and never a PR opened on intent stated earlier. It stops only when blocked (a blocking finding, red lint or type-check, a conflict, a needed force-push, no verify yet) or asks one batched question for unknown values (base branch, branch name, PR title parts).
- Paired PRs declare their merge dependency in chat and in each PR body (order-dependent or safe together; what QA must wait for).
- Every PR the assistant creates is assigned to the user (`assignee` in `workflow.json`, default: the authenticated `gh` user).
- No AI attribution in commits or PR bodies (no co-author trailers, no "generated with" footers). Commits stay conventional. PR bodies carry Scope (who narrowed the ticket and when, what was already covered, out-of-scope items with reasons), Decisions, and a Verification record; screenshots are referenced by hosted URL, never committed as assets.
- Direct pushes to protected branches (`protected` in `workflow.json`, default `main`, `master`, `develop`) happen only on explicit per-instance permission in that conversation; never carried over.
- Source → target is stated in one line before any push, PR or base change. Branches are cut from `origin/<base>` after a fetch, never from the local copy. Force-push is denied by the git guard hook; when a plan rewrites a pushed branch the assistant says so at plan time and either hands the user the exact `--force-with-lease=<branch>:<known remote sha>` command at the push step or keeps history append-only. An interrupted or "rejected" git call may still have run: after any interrupt or timeout around commit, push or rebase the real state is checked (`git log -1`, `git status --short`, `git ls-remote origin <ref>`) before reporting or retrying. `git commit -F -` fails under lint-staged (stdin consumed): the message goes to a scratch file and `git commit -F <path>`.
- Commits by other agents on the branch are verified before building on them: pull, read the diff, run tests.
- Review bots are never @-mentioned unless the team's adapter says which ones respond; replies are plain text, with evidence, and only threads the assistant replied to are resolved.
