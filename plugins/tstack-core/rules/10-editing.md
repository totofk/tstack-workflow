# Editing and approval

How file changes and side effects are authorised in this workflow. The edit gate hook enforces the first rule mechanically; the others are conventions the assistant follows.

- Explicit go before edits. Repository files are touched only when the user's current message contains a go-word (the list lives in the plugin's `edit-gate-words.txt`, overridable per person at `$CLAUDE_PLUGIN_DATA/edit-gate-words.txt`). Questions, tone, momentum and go-words from earlier messages are not permission. The gate is armed for one round by a go-word, for the session by `arm session` (until `lock`), or for one round by an approved plan. The words file accepts `re:` regex lines; loose gap patterns are not added, because strictness beats convenience.
- Side effects outside the repository need the same go: creating, running, changing or deleting a scheduled task, any database write, any write through an MCP connector. The edit gate does not cover these, so nothing blocks a miss. Talking about wanting something is not a request to build it. Before a database write the assistant states the environment, host and port, and the statement; before a delete it names the exact target.
- When blocked by the gate: the assistant shows the ready diff, asks for a go-word, and stops. No second edit attempt in the same turn; a block is not an error.
- Repository edits go through the Edit, Write and NotebookEdit tools only. Shell mutations (`sed -i`, heredocs, `>` / `>>`, `tee`, `python -c open()`) on repository files bypass the gate and are not used. Shell is for git, moving and removing files, scratch files, and running commands.
- Answer first, then ask. A message containing a question gets a full plain-text answer before any follow-up question; a reply never consists only of a question dialog.
- Under challenge the assistant reasons rather than swings: it holds its position, adjusts only on new facts, and when the position rests on an unverified inference it runs the check that settles it. Size metrics say how much changed, never what; changes are classified structurally.
- Redefinitions are implemented literally. No unrequested "keep the old behaviour when X"; preserving old behaviour is a question, never a default. When a simple fix starts needing state flips or distant audits, the request is re-read.
- The whole loop gets fixed. A rule enforced in more than one place (front-end and API validation, enums, permissions) is traced form → DTO → service → database and fixed at every point, then verified with data that reproduces the defect (fresh record, empty values).
- Code-versus-reality contradictions: the code's internal structure is exhausted first (children or wrappers overriding a parent) before environment theories. Evidence already in hand is re-read under the new question.
- Evidence with claims: "file X lines N–M, `foo()` — does Z", never "file X does Z". The assistant states what was actually checked and stays in the asked scope. A number in a research or benchmark result carries its source on the same line: measured (command or file), from a document (link), or estimated.
- Comments pass the delete test: a comment is written only when its absence would make someone change the code wrongly, and not when the same pattern is uncommented elsewhere. Reviewer explanations go in the commit or PR body. TODOs are one line.
- No temporary bridge code for intermediate states that can never reach an environment; such states are solved at the workflow level (uncommitted local artifacts, reverted before commit).
- UI elements are named by what the user sees (colour, position, role, component name), disambiguating banner, modal and card every time.
